# 项目交接

让接手对话拿到当前成果、有效决定和明确的第一步，不用用户重述，也不会两个对话同时改。适用于代码、文档、研究和媒体制作。提醒、保存、新建接续是三个动作，各有各的授权：提醒不写文件，保存不开新对话，新建接续只在用户确认了具体提议之后。pi 没有“新建并打开对话”的工具，接续降级为交付可复制的开场白，由用户手动开新会话。

## 评估：什么时候值得建议换对话

只用当前任务已有的事实判断：用户决定、验证结果、文件和任务的真实状态、扩展注入的压缩计数与规模信号。不翻私人历史，不为评估另调模型，也不按聊天轮数或感觉估算压缩次数——自动压缩次数和上下文规模以扩展注入的状态行为准。

| 条件 | 看什么 | 为什么 |
| --- | --- | --- |
| 安全位置 | 当前操作已收拢；成果、验证和后台任务的归属都能定位；该用户验收的不写成已验收 | 接手时不能有半截写入或没人认领的任务，否则两边都以为对方在管 |
| 明确后续 | 目标、范围、下一步和完成标准清楚，新对话能确定第一步 | 没有第一步的交接只是存档，新对话还得回头问用户 |
| 切换收益 | 能说出这次的具体好处：已结束的大量探索和后续执行分开、已纠正的旧路线不再带入、长上下文的恢复慢／每轮成本高／注意力稀释被切断 | 换对话有成本：重读材料、丢隐性上下文。只有旧上下文会拖累下一步时才值得 |

触发评估的信号分两类，优先级不同：

- **阶段边界（一等信号，与压缩次数无关）**：完成一个可验收阶段、准备进入下一大段工作、发现已核实的目标或版本混淆。信号出现就立即评估，前两条满足时用 `prepare`（`reason: stage`；混淆纠正后用 `confusion`）提出建议，**不等冷却**。同阶段改版本、调参、重渲染不算新阶段；同一混淆只提醒一次。普通报错、正常改需求、对话变长都不是混淆。
- **兜底节奏（没有明显阶段边界时）**：第 3 次自动压缩后，或上下文规模到扩展标记的检查点时，评估一次，前两次压缩不因次数提醒。之后按兜底再提醒需距上次正式提醒又过了 3 次压缩，或规模检查点再次到达（约再涨 50%）。

其余规则：

- 目标或权限还不清楚时先补缺项。换对话不解决阻塞、失败原因或待验收的步骤。
- 纯问答、任务已结束、讨论本 Skill：登记不适用。
- 每次扩展标记检查点，都必须用 `handoff_state` 工具登记一次结果（`evaluate` 暂缓/不适用，或 `prepare` 提出建议）；暂缓要写原因和下次检查时机。没有扩展注入时自检，不要声称有程序兜底。

## 展示

决定提醒且用户尚未回应时，建议放在最终答复正文第一段，在成果列表和任务卡之前，以“交接建议：”开头，一段话写清具体原因、接续第一步和确认后会做的动作。放最前，是因为用户通常只看开头和结尾，扩展的最终核验也只认首段；进度消息不算展示。不要放进引用、示例或代码块。例句只示范格式，不是项目事实：

> 交接建议：资料筛选已完成，后续进入方案编写，适合只带入已选资料与约束。确认后我会保存材料，并交付新会话的接续开场白，核对后继续编写方案。

pi 不能新建并打开对话，建议中的动作写成“保存材料并交付接续开场白”。已交付的建议不在以后每轮重贴；用户已回应、建议失效或任务已无后续时用 `handoff_state cancel` 作废。

## 用户回应与边界

- “先不交接”“继续做”：登记 `respond continue`，从回应时再冷却 3 次压缩。普通工作指令里的“继续”既不是回应，也不是交接批准。
- “做完 X 再提醒”：登记 `respond defer` 并写节点，到 X 再评估，不另加次数门槛。
- “本任务不提醒”：登记 `mute`，关闭主动提醒直到用户恢复；显式交接请求仍执行。
- 没人回应：继续已授权工作，不追问、不自动保存、不交付接续材料。提醒本身不授权写文件、停止任务或开新会话。
- 规则只放本 Skill 及配套扩展，不写入全局配置、不加定时任务、不改压缩阈值。保存和接续仍按已有授权与 pi 边界执行。
